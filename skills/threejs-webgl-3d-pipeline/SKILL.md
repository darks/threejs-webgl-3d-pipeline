# Three.js / WebGL 六阶段场景制作

交付可运行、可交互、经过独立 Agent 实际截图评审的 3D 工程和可追溯的迭代记录。采用六阶段、多 Agent 讨论与制评分离设计：用最小上下文交接减少记忆噪点，用独立评审避免实现者自我放行。本技能包包含必要执行规则，安装后不依赖仓库外的工作流文件。美术方向服从用户需求；高质量不等于强制写实。

## 执行入口

- 默认在交付的 HTML 场景单页提供「导出 GLB」与「导出 OBJ」按钮（或同一导出菜单中的两个格式选项），无需用户另行提出；用户明确排除导出时遵从其要求。导出属于交付功能，在阶段三实现、阶段六按最终版本复验，细节见执行与产物契约的“模型导出”。
- 新场景按六阶段推进。已有工程先检查现状，复用有效产物，从最早缺失或受变更影响的阶段继续；小修复不启动完整管线。
- 完整管线必须使用真实的多个 Agent 会话，不能由同一会话模拟角色对话或评审自己的实现。优先使用宿主子代理；只有必要时使用外部 CLI。并发不是必需条件，槽位不足时按依赖串行调度独立会话。
- 自行决定可逆的实现细节，将影响结果的假设写入 SPEC。只有缺失信息实质影响目标或依赖确实阻塞时才询问；内部决定不能表述为用户要求。
- 明确目标工程绝对路径，在工程内工作；技能目录只保存技能资源。沿用现有技术栈、目录和包管理器，不默认重建工程。
- 实现前读取 [执行与产物契约](references/execution-contract.md)。仅在需要外部 CLI 时使用其中的 CLI 部分；外部脚本正常退出不能代替阶段验收。

## Agent 分工与上下文隔离

- 主控负责用户沟通、任务交接、集成调度、证据核验和阶段状态；将设计、实现和视觉评分交给阶段执行者。主控不代写 Critic 评分，不删除不利结论，不以工期或预算要求评审放行。
- Producer 与 Director 必须为两个独立会话；Architect、Lead_Dev、Art_Director、Shader_Material 各自以新会话接收阶段交接。Lead_Dev 按模块委派 Specialist，自己负责集成；模块数量按实际工程确定，不为凑人数拆分。
- 每次视觉评审启动全新 Critic，会话不得参与本次运行的设计、编码、调参或修复。Critic 只读场景与证据、返回报告；实现者修复后交给新的 Critic 复审。换角色名或清理聊天摘要不等于独立会话。
- 委派时禁止默认继承完整父会话；使用宿主的新上下文选项（如支持时 `fork_turns="none"`）或独立 CLI 会话。传递用户相关原话、当前约束及阶段必需产物，保留来源；不传递试错聊天、实现者的自评或预期分数。具体交接字段、角色权限及评审顺序见执行契约。
- 启动前检查独立会话、图像查看和工具能力。没有可用的隔离执行方式时记录 `blocked` 并说明缺失能力，不静默退化为单 Agent 自评。只有用户明确接受降级才继续，记录被豁免要求，交付不得声称完成独立多 Agent 验收。

## 运行约定

新任务创建唯一 `runId`，产物放在 `artifacts/<runId>/`，下文用 `RUN` 表示。工程根保存 `SPEC.md`、`BLUEPRINT.json`、`PLAN.md` 和 `tuning_params.json`；已有等价配置时记录映射并复用。

`RUN/state.json` 记录阶段、状态、假设、检查命令及结果、产物路径和剩余问题。状态为 `pending / running / passed / blocked / failed / skipped`。产物有效且检查成功才能 passed；可选能力缺失记为 skipped 并说明降级，关键运行或视觉验证缺失不能宣称完整验收。

默认预算：几何评审最多 **5 次**；光影候选 **2–3 组**，该阶段独立评审最多 **3 次**；最终材质改进最多 **2 轮**。尊重用户指定预算，复核也计入对应阶段评审预算。达到上限仍不达标则保留可运行版本、截图和剩余问题，停止依赖该验收的后续阶段，不无限重试或降低阈值。

## 阶段一：需求与视觉基准

1. 主控分别启动 Producer 与 Director。Producer 根据用户原始需求提出 5–10 个关键问题，覆盖视角、尺度、主体、交互、碰撞、风格、光线和设备；Director 回答并提出方案；Producer 检查回答中的遗漏和矛盾。默认 1–2 轮问答，Director 将结论固化为 SPEC，仍有重大分歧时由主控依据用户目标裁决，缺少关键用户信息才询问。保存双方实际输出及决策依据到 `RUN/discussion.md`，不得由主控编造双方对话。
2. SPEC 写明用户目标、明确标注的假设、核心交互验收用例、美术方向、目标视口/设备及可测的性能预算。预算匹配任务，不统一强加面数或帧率。将默认 OBJ/GLB 导出范围、格式差异和下载验收写入 SPEC；沿用场景单位与坐标系。
3. 有生图工具时生成并实际查看 `RUN/concept_target.png`；已有参考可直接作为基准，记录来源与采用的构图特征。
4. 生图不可用时，以 SVG 布局色稿或文字风格说明继续，明确它不是生成的概念图。用户明确要求生图但能力缺失时说明阻塞。

**验收**：规格能指导构建，核心交互有可执行用例，视觉基准存在或降级已记录。

## 阶段二：空间蓝图与计划

1. 新建 Architect 会话，只交接已锁定的 SPEC、视觉基准和相关工程约束。沿用现有坐标系；新工程默认 Y 向上、1 unit = 1 meter，定义原点、正 Z 方向、旋转单位和世界/局部坐标约定。
2. 蓝图定义相机、模块变换、尺寸、边界、连接点及碰撞区域。模式统一为 `overview / closeup / lowangle`；`wireframe` 复用 overview。
3. AABB 用于粗筛，不等于真实碰撞。父子装配、地面接触及有意嵌入允许交叠，记录允许关系；旋转模块的世界 AABB 由变换后边界计算。
4. 涉及斜坡、拱桥或起伏地形时，在蓝图定义承载面及附着关系，按执行契约的“曲面与附着”部分统一采样高度、法线和路径切线。区分跟随坡面的物件与保持竖直的立柱；多层结构不能只用一个全局高度函数。
5. 单张参考图不能唯一确定尺度或 FOV：标注估计值、尺度锚点及不确定项，再用渲染校准。
6. PLAN 记录模块职责、依赖、文件归属、合并接口、截图方案和验收顺序。由 Lead_Dev 将模块任务委派给独立 Specialist；共享接口先确定，依赖任务串行，禁止多个执行者同时修改同一文件。

**验收**：JSON 可解析、模块 ID 唯一、数值有限、尺寸及相机参数有效，布局可解释，无已知非预期重大交叠。

## 阶段三：构建、参数、导出与截图接口

1. 新建 Lead_Dev 会话，接收 SPEC、BLUEPRINT 和 PLAN，按计划向 Specialist 下发最小模块资料并集成产物。沿用工程框架；空工程可选 Vite + Three.js，简单场景可用 ES modules。按复杂度拆分模块，统一坐标和资源释放约定，不制造空模块凑目录。
2. 构建场景和核心交互。将需要比较调整的曝光、灯光、颜色、雾、材质及机位集中到参数配置，给出默认值和范围；常规算法常量无需全部配置化。
3. 按执行契约实现 `window.sceneReady`、`window.setCameraMode(mode)`、`window.applyTuningParams(params)` 及 `?clean=1`。更新必须真实影响渲染，正确处理投影、控制器及后处理。
4. 创建或适配 `scripts/capture_views.mjs`，输出确定性四视图、manifest，失败时退出非零。优先正常绘制后截图；确需读取绘图缓冲时才启用 preserveDrawingBuffer。
5. 曲面场景复用统一表面采样实现几何、物件放置及需要的碰撞查询；按契约检查底部接触点、坡度变化、跨段连接和桥上/桥下分层。高度对齐不等于朝向或整个底面已经贴合。
6. 按执行契约的“模型导出”实现单页上的 OBJ/GLB 导出控件，导出真实模型，提供忙碌与失败反馈；`?clean=1` 隐藏导出控件。
7. 运行已有构建检查、浏览器加载和核心交互用例，实际点击两种导出并重新载入下载文件验证，检查运行时异常与必要资源失败，再生成首套四视图。

**验收**：能启动，必要构建检查通过，交互可执行，OBJ/GLB 导出检查通过（用户明确排除时记录原因），四张图有效且视图切换真实生效；无法运行浏览器时标记视觉验证阻塞。

## 阶段四：有证据的几何与布局评审

1. 主控冻结本轮源码与参数，启动全新、未参与实现的只读 Critic，交接四视图、manifest、SPEC、蓝图、可用概念图和原始检查证据。Critic 实际打开图像或查看附件；只读取文件名不算视觉评审。先独立评估当前版本，再查看历史缺陷逐项复核，不提前提供历史评分或实现者解释。
2. 几何比例、布局与穿模、光影构图、材质与目标风格一致性四项分别打 0–10 分并说明依据。评分不能替代构建、交互或碰撞验证。
3. 只列有证据的缺陷，允许零条。注明严重程度、视图/模块、观察现象和修复验收方法；不为凑数量编造问题。
4. Critic 返回契约规定的 JSON，由主控原样保存到 `RUN/pass_N/critic.json`，核验会话身份、证据与版本后计算通过条件：均分 ≥ 9.0、无未解决 blocker/major、必要工程检查通过。主控不得修改评分或代替 Critic 关闭问题。
5. 未通过则把缺陷工单交给 Lead_Dev 修复，重跑受影响检查、重新截图并启动新的 Critic。修改后不能沿用旧结论。第 5 次未通过即停止，不再做未验证的最后一轮修改；不能通过额外换评审者绕过预算或挑选有利报告。

**验收**：当前源码与参数对应的图像已通过，依据已保存。不复用其他运行的 PASS_LOCKED 文件。

## 阶段五：光影调参与画廊

1. 新建 Art_Director 会话，交接 SPEC、已通过版本的截图与参数，固定几何与交互，只调整已有可调参数；允许新增截图、参数快照、报告及画廊。缺少必要接口时交回 Lead_Dev 补齐并独立复核。
2. 在相同相机、视口、种子和动画时刻比较 2–3 组候选，每组保存完整参数及截图；按 SPEC 选择，不以更亮或更写实作为通用标准。
3. 优选方案写入默认配置，重新加载和截图验证与候选一致。由全新 Critic 按阶段四条件独立复核最终候选。候选组数按不同参数快照计数，评审次数按实际 Critic 调用单独计数；复核已有候选不增加组数。失败时可在剩余组数内调整或改选已有候选，但仍须有剩余评审次数；任一所需预算耗尽时停止后续阶段。
4. 工程根生成 `progress.html`，以相对路径呈现概念基准、截图、缺陷、分数、候选参数及选择理由。保留已有运行记录，不捏造缺失截图或评分。

**验收**：默认参数实际生效，画廊资源可访问，选择结果有比较依据。

## 阶段六：目标对照与材质精修

1. 获取阶段五无 UI overview 截图。有图生图工具时，以它生成保持构图和布局的目标图，写实项目使用写实目标，风格化项目保留风格。长边至少 2048 px，检查真实尺寸后才命名为 `RUN/2k_photoreal_target.png`（写实）或 `RUN/2k_style_target.png`（其他）。
2. 无生图工具时记录跳过目标图生成，按已有参考检查材质，不伪称完成图像差分。目标图改变结构或机位时标记偏差，不强迫场景匹配生成错误。
3. 新建 Shader_Material 会话，交接 SPEC、通过版本、相关模块与目标图，针对观察到的差距改进纹理尺度、粗糙度、倒角、接触阴影和反射等，兼顾性能。Image_Gen 职责由具备生图能力的 Agent 或主控调用生图工具承担，不能因此兼任 Critic。禁止把目标图贴成背景板替代应有三维结构；正常环境贴图和背景允许使用。
4. 开始前保存可恢复的通过版本。最多 2 轮“改进 → 检查 → 四视图 → 全新 Critic 独立评审”，沿用阶段四通过条件检查回归。失败时恢复通过版本并重新验证，或明确交付未通过状态。
5. 按最终源码和参数复验 OBJ/GLB 导出，保存匹配版本的样例文件及检查记录；材质或几何变化后不能沿用旧导出结果。
6. 更新画廊和 state，交付工程路径、启动命令、单页导出入口、实际通过的检查、截图/画廊入口、剩余问题及降级项；性能数据只报告实测值。

**验收**：最终运行版本、默认参数、截图及评审一致，核心交互、构建和最终模型导出检查通过，视觉与性能结论有证据。
